# Unified offerwall setup

ExpertsTeam supports separate server-to-server adapters for Torox, AdGate Rewards, CPX Research and Lootably. Each provider must approve the ExpertsTeam publisher placement before its wall is activated. Never put a provider secret in a `VITE_` variable.

## Server environment

Set these as server-only deployment environment variables:

| Provider | Required server variables | Optional |
|---|---|---|
| Torox | `TOROX_PLACEMENT_ID`, `TOROX_APP_TOKEN` | `TOROX_CREDITS_PER_UNIT`, `TOROX_ALLOWED_IPS` |
| AdGate Rewards | `ADGATE_ALLOWED_IPS` | `ADGATE_CREDITS_PER_UNIT` |
| CPX Research | `CPX_APP_ID`, `CPX_APP_SECRET`, `CPX_POSTBACK_SECRET` | `CPX_POSTBACK_HASH_MODE`, `CPX_ALLOWED_IPS`, `CPX_CREDITS_PER_UNIT` |
| Lootably | `LOOTABLY_WEBHOOK_SECRET` or `LOOTABLY_POSTBACK_SECRET` | `LOOTABLY_CREDITS_PER_UNIT` |

All `*_CREDITS_PER_UNIT` values default to `1`. Set an explicit conversion factor for each placement after checking the partner's reward currency and the ExpertsTeam credit economics. The server rejects non-positive or excessive conversion factors and rewards.

Optional geo-routing variables: `TOROX_ALLOWED_COUNTRIES`, `ADGATE_ALLOWED_COUNTRIES`, `CPX_ALLOWED_COUNTRIES`, and `LOOTABLY_ALLOWED_COUNTRIES` accept comma-separated ISO-3166 alpha-2 country codes. Matching `*_BLOCKED_COUNTRIES` variables can explicitly exclude countries. If no allowlist is configured, the provider remains available in all detected countries. The geo endpoint uses the hosting platform's country header and does not expose the visitor's IP address.

Client-visible placement settings:

- `VITE_ADGATE_WALL_ID`: AdGate Rewards wall ID.
- `VITE_LOOTABLY_IFRAME_TEMPLATE`: the HTTPS iFrame URL copied from the Lootably placement with its user-ID placeholder replaced by the literal `{USER_ID}`.

CPX's app ID and per-user secure hash are generated by the server. Torox's session URL is generated server-side using the placement token; the token is never returned to the browser.

## Callback URLs and parameters

Configure these HTTPS endpoints in each publisher dashboard:

| Provider | Callback URL | Required values |
|---|---|---|
| Torox | `/api/offerwall/torox/postback` | `id`, `oid`, `user_id`, `amount`, `payout`, `o_name`, `sig`, `ip_address` |
| AdGate Rewards | `/api/offerwall/adgate/postback` | `conversion_id`, `s1`, `points`, `payout`, `state`, `session_ip` |
| CPX Research | `/api/offerwall/cpx/postback` | `trans_id`, `user_id`, `status`, `amount_local`, `amount_usd`, `hash` |
| Lootably | `/api/offerwall/lootably/postback` | Prefer the Conversion Webhook with `x-lootably-webhook-secret`; GET postbacks use `userID`, `transactionID`, `ip`, `revenue`, `currencyReward`, `hash`, and optional `status` |

Security behavior:

- Torox signatures use its documented MD5 value `oid-user_id-app-token`; the callback IP allowlist includes Torox's published `44.212.211.226` address and can be extended with `TOROX_ALLOWED_IPS`.
- AdGate does not provide a signed callback in its basic integration. Configure `ADGATE_ALLOWED_IPS` with the exact source IPs supplied in the AdGate publisher dashboard. The endpoint fails closed if this allowlist is missing.
- CPX's callback hash format can vary by publisher dashboard setup. The default `CPX_POSTBACK_HASH_MODE=md5_trans_id_secret` checks `MD5(trans_id-CPX_POSTBACK_SECRET)`; `md5_user_trans_id_secret` checks `MD5(user_id-trans_id-CPX_POSTBACK_SECRET)`. Confirm the exact callback hash with CPX's publisher dashboard and run its postback tester before enabling real rewards. Unknown modes fail closed.
- Lootably Conversion Webhooks validate the `x-lootably-webhook-secret` header. The legacy GET postback validates SHA-256 of `userID + ip + revenue + currencyReward + postback secret`.

Every accepted callback is processed by a service-role-only database function. Provider event IDs are unique per network. Duplicate callbacks do not double-credit. Reversals remove available credits; any amount already spent is recorded as credit debt and blocks further AI usage until future rewards clear it. The user ledger records awards and deductions.

## Credit top-ups

The Earn page supports four payment methods. Configure rates and payment instructions in Admin → CPA credits before enabling a method. The database stores a snapshot of the conversion rate on each order.

- Mobile Money, Airtel Money and crypto orders require the member's payment transaction reference and an administrator's approval.
- Stripe uses Checkout. Set server-only `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and `APP_URL`. Register `/api/stripe/credits/webhook` as a Stripe webhook endpoint for `checkout.session.completed` and `checkout.session.async_payment_succeeded`.
- Stripe orders are credited only after the signed webhook is verified and the order ID, Checkout Session ID, currency and total amount match the stored order.
- Never enable a rate until the payment instructions and credit conversion have been checked.

## Launch checklist

1. Create and get approval for each publisher placement.
2. Add its credentials to the server environment; never commit secrets.
3. Set the public wall ID or URL template only where required.
4. Configure the callback URL and provider macros exactly as listed.
5. Configure the provider-specific credit conversion factor.
6. Run the provider's own test callback and verify the response body is `1`.
7. Confirm the transaction appears once in `offerwall_provider_events` and the member ledger.
8. Test a duplicate callback and a reversal before enabling live traffic.

A provider is not considered live merely because its wall ID exists. It must pass its publisher-dashboard callback test and have the server secrets and allowlists configured.
